# Coherence Database Web App: Requirements

This document specifies what the Coherence database web application must provide. "Must" indicates a mandatory requirement; "should" indicates a strong default. Technical terms are defined at first use.

## 1. Purpose and Core Guarantees

1. **Identical calculation behaviour:** Move Coherence from a command-line workflow over frozen folders to a web application backed by a relational database while keeping the five calculation phases (`assign`, `attribute`, `bible`, `adjust`, `emit`) and their business semantics unchanged.
2. **Immutable audit history:** Nothing is ever overwritten or deleted in business records. Every change appends a new record that replaces, reverses, or extends an earlier record and references it, allowing any historical moment to be reconstructed.
3. **Database-enforced integrity:** PostgreSQL 17 (a relational database management system) must enforce immutability, state transitions, uniqueness bounds, path rules, and cryptographic commitments directly through constraints and triggers (database rules that execute automatically on writes), so integrity never relies on application code behaving correctly.
4. **Reference environment isolation:** Existing standalone reference runs and their folders remain untouched and read-only during migration and verification.
5. **Code protection and data ownership:** Customers own their input and output data and receive only their data on handover. Customers never have access to Nusear's code, engine binaries, wrapper scripts, or compiled review pages and viewers under any circumstances. Code and code-bearing files live exclusively in Nusear's environment.
6. **Tenant isolation:** Each company has its own dedicated database inside Nusear's cloud organization and its own separate data storage vault (holding its inputs, outputs delivered to it, and exports).

## 2. Scope

- **In scope:** Per-company PostgreSQL 17 databases; idempotent per-company database provisioning (`scripts/provision-company-db.mjs`) and read-only history import into a provisioned database (`scripts/import-history.mjs`); separated Nusear code store and company data stores; the engine worker; server-side web handlers and HTTP (Hypertext Transfer Protocol) endpoints for Coherence screens; substance and storage verification proofs; database-backed downstream readers for Nusear's tools and signed agent feeds.
- **Out of scope:** Modifying Coherence's own calculation engine source code; outbound email or statement delivery; external scheduling or cloud infrastructure creation scripts.

## 3. Platform and Cloud Topology

1. **Database placement (efficient plan):** One Cloud SQL PostgreSQL 17 server per environment (separate development and production servers in completely separate Google Cloud projects inside Nusear's cloud organization), each holding one dedicated PostgreSQL database per company plus Nusear's control database (`nusear_control`). Development and production environments remain completely separate (`iam.database_context.environment` binds signing keys and tokens to one environment). Each company's data storage vault (inputs, delivered outputs, and exports) remains separated per company.
2. **One database per company:** Each onboarded company gets its own dedicated PostgreSQL database on the environment's Cloud SQL server. Everyday development and automated tests run against a local PostgreSQL 17 instance using throwaway `coherence_test_*` databases.
3. **Application and engine runtime:** The web server and worker run on Node.js using the standard `pg` driver. The Coherence engine runs unchanged as Python code in an isolated workspace prepared by the worker.
4. **Object storage:** Large files live in create-only object storage buckets addressed strictly by their SHA-256 cryptographic fingerprint (a 64-character lowercase hexadecimal digest uniquely identifying exact bytes). The database stores fingerprints, byte sizes, MD5 and CRC32C storage checksums, and structured facts.

## 4. Actors and Permissions

1. **Nusear owner:** Full read and write access across all companies, including typed high-impact decisions (Emit confirmation, recording statements as sent, carrying approvals, abandoning runs, engine registration, and historical imports).
2. **Nusear staff:** Access restricted to assigned companies (`customers`) and denied on Coherence run commands when `run-coherence` is in `withheld`. Staff cannot execute owner-only typed decisions.
3. **Company administrators:** Read-only access to the whole Coherence workshop (`runs`, `inputs`, `outputs`, `decisions`, `checks`, `journal`, and unfinished runs via full-tenant `act:coherence.unpublished.read`), Book of Business, member details, real vendor names, and HR records. Holding the whole workshop includes the amounts inside reviews, decisions, and checks (approved amounts on decisions and approval rows, review configs and drafts, and check reports), while agency statements, upline statements, the Coherent Ledger, and Book of Business money columns (`statements`/`statement_cash`, `upline`/`ledger`/`upline_cash`) stay gated by revenue rights, and payroll, lead costs, and billing/referrals remain off unless explicitly granted; administrators are never allowed to read code-bearing files or write to Coherence.
4. **Recipients (per-recipient viewers dropped):** Per-recipient bundle serving is not built, and no recipient is authorized by display name or folder position. Recipients have no access to Coherence management endpoints. Any future recipient views will be served as dedicated application screens backed by permission-scoped database views and separated tables. The engine's Emit outputs are still archived whole as history, with code-bearing HTML (Hypertext Markup Language) pages stored solely in Nusear's code store.
5. **View-As refusal and support acting-for:** "View as" sessions must refuse every write command unconditionally. Support staff explicitly acting on behalf of a company (`actingFor`) may write within their role and must record `actingFor` in every resulting journal entry.
6. **Engine worker service identity and single database command surface:** Every write (web, worker, reconciler, history imports, and proof tooling) executes strictly through PostgreSQL `app_cmd.coherence_*` commands using a real signed `app.session_token` via `withRequestTx`, journaled in both `coherence.journal_entries` and `platform.audit_journal` with no privileged bypass or actor-without-token fallback. A dedicated service identity (`platform_worker` with a mandatory signed `workerToken`) is the sole actor allowed to start, finish, fail, cancel, or interrupt step attempts, expire old drafts, and accept or reject queued review submissions; human actors cannot execute worker-only commands, and the worker cannot execute human decision commands.
7. **Database-enforced IAM scope (Release 1 first-user surface + Release E2 isolation + Release E4 explicit-people):** All read and write access is enforced inside PostgreSQL via signed `app.session_token` tokens, `FORCE ROW LEVEL SECURITY`, `app_views.*` security-barrier views, shared `platform_view_owner` per-data-kind read-rights functions (`app_views._read_*`), and `app_cmd.*` commands using one unified time-consistent organization closure and grant evaluator (`iam.v_organization_closure`, `iam.v_organization_closure_live`, `iam.person_effective_grants`) supporting `org_subtree`, `self`, and `explicit_people` person scopes, dated `valid_range` and `data_date_range`, right retirements, per-organization tool switches (with ancestor `held`/`off` veto and Nusear-internal bypass), and View-as intersection with unconditional read-only enforcement. In `iam.v_organization_closure`, every chain carries the intersection of its links' date ranges (`eff_range`) and is kept only while non-empty (`iam.v_organization_closure_live` stays today's live tree): a moved agency's history stays under its old company while teams added after the move never enter the old company's tree, old teams from before the move never enter the new upline's tree, grants anchored at the new upline never reach the old company's working database, and no customer grant reaches across companies through a holding company (the holding-company user-grant branch is deleted in Release E2; holding-company executives receive a separate user at each company, while live parent tool switches still govern switch vetoes). Deferred mechanisms not required yet (supervision chains, connection scopes, customer self-service role delegation triggers, person contacts, and contractor ceiling) remain parked until a customer needs them.

9. **The run workshop, finished goods, and member column rights (Release E1, 2026-11-25):** Coherence's read surface is split into two plain layers:
   - **The run workshop (all or nothing):** Every read gated by `act:coherence.runs.read`, `act:coherence.inputs.read`, `act:coherence.decisions.read`, `act:coherence.checks.read`, or `act:coherence.journal.read` (runs, step attempts, step and cancel requests, carries, abandonments, emit confirmations, review saves, review configs, review drafts and submissions, approval rows, decisions, decision commits, standing and snapshot input versions, input entries and changes, staging files, engine versions, checks, the journal, journal and review-drift gates, run stage lookups, and unsent run outputs) goes through one shared check (`app_views._read_workshop_right`): full-tenant workshop right together with full-tenant `act:coherence.unpublished.read` (`app_views._read_has_full_tenant_right`, covering the company and all descendants, never house-only `include_descendants = false`). `app_views._read_has_run_meta_access()` and `app_views._read_can_see_unsent_run_meta()` count `act:coherence.runs.read` only through `app_views._read_workshop_right('act:coherence.runs.read')` (leaving the four finished-goods rights `bob.read`, `statements.read`, `upline.read`, and `ledger.read` unchanged), so callers with `runs.read` alone or with house-only or partial `unpublished.read` get zero rows from `app_views.coherence_published_runs`, `null` from `findLatestPublishedRun()`, and no unsent rows from `app_views._read_published_emit_attempts()` or `_read_published_emit_attempt_ids(false)`. Whoever passes sees all of the workshop for their granted areas, unfinished runs included; whoever does not sees none of it. The owner, entity managers, Nusear staff, and company administrators hold workshop access (`unpublished.read` included).
   - **Finished goods:** Everyone else (agency managers, selling and retention agents, investors, and statements-only readers) reads only finished goods: the Book of Business, agency and upline statements, Coherent Ledger, reconciliation, sent outputs, and entity bundles, kept to sent runs via `app_views._read_published_emit_attempts` and `app_views.coherence_published_runs`.
   - **Member data, file handles, free text, and check reports:** Member PHI (`col:coherence.member_phi`, sensitivity class `member_phi`) and member contact details (`col:coherence.member_contact`, sensitivity class `member_contact`) are gated in PostgreSQL `app_views.*` via four shared single-evaluation `platform_view_owner` InitPlan/hashed-SubPlan helpers (`app_views._read_member_phi_wide_orgs`, `app_views._read_member_phi_narrow_pairs`, `app_views._read_member_contact_wide_orgs`, `app_views._read_member_contact_narrow_pairs`): `mbi`, `member`, and `dob` in `coherence_bob` / `v_current_policy_periods` require `col:coherence.member_phi`; `phone`, `email`, `address`, and `county` require `col:coherence.member_contact` (`state` remains visible); `conflicts` in `coherence_bob` / `v_current_policy_periods` requires both `col:coherence.upline_cash` and `col:coherence.member_phi`; `mbi`, `member`, `record_id`, `reversal_of`, `corrects_record_id`, `reason`, and `notes` in statement agency/upline/entity/membership views and `mbi`, `member`, `record_id`, `notes`, and `coherent_notes` in ledger views require `col:coherence.member_phi` (with agency `record_id`/`reversal_of`/`corrects_record_id` requiring both `col:coherence.statement_cash` and `col:coherence.member_phi`); inside the workshop, `record_id` and `note` in `coherence_decisions` and `coherence_approval_rows`, `approvals_file_sha256` in `coherence_approval_rows`, `coherence_review_saves`, and `coherence_runs.prior_approvals_sha256`, `log_file_sha256`/`log_md5_b64`/`log_crc32c_b64`/`error_summary` in `coherence_step_attempt_events`, `body` in `app_views.coherence_journal` (requiring full-tenant `col:coherence.member_phi`, and all eight tenant-wide entity-finance and member rights via `app_views._read_has_full_entity_finance()` for `command_kind IN ('carry_sent', 'materialize_emit')`, matching `coherence_carries.file_sha256` and ledger totals), and `report` JSONB payloads in `coherence_checks` (including run-less `import`, `overlay_reconstruction`, and `objects` reports that carry member-data file hashes, and `POST /checks/run`, which reads its recorded `report` back through `app_views.coherence_checks` so it masks identically to `GET /checks`) require full-tenant `col:coherence.member_phi`; `coherence_review_drafts`, `coherence_review_submissions`, and `coherence_review_configs` (and their underlying `review_drafts_iam_read`, `review_submissions_iam_read`, `artifacts_iam_read`, and `stored_files_iam_read` decision branches) require full-tenant `col:coherence.member_phi` alongside workshop `act:coherence.decisions.read` (handlers also retain `redactPhi` on `error_summary`, `result_message`, and step logs); whole-file `coherence_entity_bundle_artifacts`, `emits/*` in `coherence_run_outputs`, and `carry_kind = 'sent'` `file_sha256` handles in `coherence_carries` require all eight full-tenant rights via `app_views._read_has_full_entity_finance()` (while `approvals` and `decisions` carries require full-tenant `col:coherence.member_phi`, and `run.json`/`company_manifest.json` remain exempt on sent runs for `outputs.read` and on all runs for workshop `outputs.read`);    - **Full-tenant scope rule (Release E1 + Release E2):** Both the run workshop (`app_views._read_workshop_right`) and whole-company outputs (`app_views._read_has_full_tenant_right`, `app_views._read_has_full_entity_finance`) require the governing right across the whole company, meaning every agency and team in its organization tree, history included. Therefore: (a) an agency whose `coherence` tool switch is `held` or `off` closes both the workshop and whole-company outputs to the company's own people while Nusear's people are not affected; and (b) company-anchored users and Nusear's people remain open when archived or moved-out agencies exist. No grant reaches across companies through a holding company (the holding-company user-grant branch in `iam.person_effective_grants` is deleted in Release E2).
10. **Separate company users, per-company sign-in identities, and Nusear support isolation (Release E2, 2026-11-25):**
    - **Separate user per company, nothing shared:** Each company database holds only its own people (`principal_origin = 'company_local'`), mirrored Nusear staff (`principal_origin = 'nusear_staff'`), and service principals (`principal_origin = 'service'`). A person who works for or moves between companies receives a separate `company_local` user in each company database; holding-company executives likewise receive a separate user at each company, with zero cross-company grant flow through holding companies. Live `primary_email` and `npn` uniqueness on `iam.person_versions` is scoped by `principal_origin` so one real person can hold both a `nusear_staff` support identity and a `company_local` user in the same database without collision.
    - **Company-only writing agents:** Only `company_local` people can hold `iam.agent_affiliations` or appear as `writing_person_id` on policies, statements, and ledger rows (`coherence._resolve_writing_person_id()`, backfill, write commands, and the `BEFORE INSERT OR UPDATE` table guard on all five `writing_person_id` tables refuse `nusear_staff` and `service` principals while keeping `NULL` allowed for journal replays).
    - **Scoped signing keys with row-level security:** `iam_secret.signing_keys` enables `ROW LEVEL SECURITY` without `FORCE ROW LEVEL SECURITY` so `platform_iam_sync` sees and writes strictly `'nusear_staff'` and `'service'` keys (never reading or updating `'company_local'` web secrets), while the table owner (the same role that owns `iam.session_context()`, never `platform_iam_sync`) reads every key. `iam_secret.signing_keys.key_scope` (`'company_local'`, `'nusear_staff'`, `'service'`) is enforced inside `iam.session_context()`. A company's `company_local` web key cannot sign tokens for `nusear_staff` or `service` (worker) principals or View-as them; a `service` key cannot View-as any principal; a `nusear_staff` key may View-as a `company_local` user strictly read-only.
    - **Per-company sign-in identities:** `iam.person_auth_identities` binds `(auth_issuer, auth_subject)` from each company's own Clerk application strictly to active human `company_local` people in that company's database (and `nusear_staff` in a `control` database). `iam.resolve_auth_identity(auth_issuer, auth_subject)` is `SECURITY DEFINER` owned by `platform_readonly`, executable strictly by `platform_auth_lookup` (never `platform_app`), and returns zero rows for unknown, suspended, or revoked identities and suspended or archived users.
    - **Hard origin, control-DB, and sync boundaries:** Cross-origin role grants (`company_local` with `is_nusear_internal = true`, or `nusear_staff`/`service` with `is_nusear_internal = false`), cross-origin memberships, `company_local` people in a `control` database, and `platform_iam_sync` reads/writes of `company_local` signing keys or writes to `company_local` people/versions/memberships/grants, `agent_affiliations`, `person_auth_identities`, or company custom roles (`owner_org_id IS NOT NULL`) are refused inside PostgreSQL. Only Nusear's people, the entity tree, platform catalog, tool switches, and Nusear/service signing keys pass from Nusear into a company database.
    - **Deterministic Nusear support attribution and customer view masking:** `iam.assert_can_write()` records `recorded_as` deterministically from `principal_origin` (`'self'` for `company_local`, `'nusear_support'` for `nusear_staff` in company databases, `'service'` for service principals). Live decision writes always stamp the caller's own actor and `acting_for` (and `coherence_record_decision_baseline` and `coherence_import_historical_run` preserve non-UUID historical labels with `acting_for` as carried while refusing person UUIDs in `decided_by` by stamping caller attribution; omitted `decided_by` falls back to caller attribution in `coherence_record_decision_baseline` and `'historical_import'` in `coherence_import_historical_run`). Customer-facing views (`app_views.coherence_journal`, `app_views.coherence_decisions`, and `app_views.audit_journal`) show `'Nusear support'` (`iam.database_context.support_external_label`) for Nusear support writes whenever the caller lacks `col:platform.audit_journal.nusear_actor`, never exposing the Nusear person's name or UUID.
11. **Entities over time, dated works-for lines, per-company vendor masked names, and sync function audit (Release E3, 2026-11-25):**
    - **Per-company trees and agency moves to external uplines:** Each company database keeps its own entity tree from its own agent file; a downline company appears as a normal child in the parent company's tree without a separate reporting-tie table. `iam.organizations.org_kind` remains immutable (a referral destination, downline, or external upline becoming a Nusear customer gets its own database as `'company'`) and includes `'external_upline'` so an agency moving to a non-Nusear upline receives a dated live parent edge (`one parent per day`), staying in `iam.v_organization_closure` under the old company with its history so post-move runoff Emit runs still reconcile to `$0.00` and the agency manager's reads keep working, while the external upline and post-move teams see zero rows inside the old company's database.
    - **Dated works-for lines:** `iam.organization_memberships` replaces `capacity` with plain dated works-for lines carrying nullable `work_arrangement IN ('employee', 'self_employed_internal', 'self_employed_external')` with no default (service principals and passive investors store `NULL`, while workers record their arrangement covering individuals and personal LLCs without adding self-employed entity kinds) and nullable `tax_classification IN ('w2', '1099')` strictly as a tracking/accounting setting. Overlapping active works-for lines for the same `(person_id, organization_id)` are refused regardless of arrangement or tax classification.
    - **Per-company lead vendor masked names:** Each company sets its own masked name for a lead vendor in its own database (`iam.organization_versions.masked_display_name`), and PostgreSQL refuses any `lead_vendor` organization version without a non-blank `masked_display_name` (enforced at the read-view boundary in Release E5). Referral destination ties wait until the referral tool joins the database.
    - **Sync role function whitelist and zero function ownership:** Live catalog verification (`verifyIamConfigInvariants`) enforces an exact function-`EXECUTE` whitelist for `platform_iam_sync` covering strictly its five `SECURITY INVOKER` helpers (`platform.canonical_json`, `platform.sha256_text`, `platform.format_utc_us`, `platform.compute_journal_hash`, and `iam.business_today`) and refuses `platform_iam_sync` owning any function in any schema.

13. **IAM read views, one vendor-masking rule, and Nusear-staff-only IAM write commands (Release E5, 2026-11-26):**
    - **FORCE RLS across all 18 `iam.*` tables and 11 `app_views.iam_*` views:** Every `iam.*` base table enables and forces row-level security (`platform_app` holds zero base-table privileges; `platform_view_owner` holds zero access on `iam.person_auth_identities`). Eleven `security_barrier = true` views owned by `platform_view_owner` (`iam_my_context`, `iam_organizations`, `iam_organization_edges`, `iam_people`, `iam_memberships`, `iam_agent_affiliations`, `iam_roles`, `iam_role_rights`, `iam_role_grants`, `iam_role_grant_people`, `iam_tool_switches`, bringing `app_views.*` to 50 views) serve IAM reads under `act:iam.read` with InitPlan evaluation, hiding Nusear staff and internal roles from customers and returning zero rows for wrong-company operators, zero-rights investors, suspended users, and unauthenticated sessions.
    - **One vendor-masking rule:** Each company's masked vendor names appear on `app_views.iam_organizations` alone (with `slug` and `external_domain` set to `NULL` for everyone without `col:vendors.real_name`, except a vendor's own active people who see their own vendor real and other vendors masked, strictly intersected under View-as). Every IAM audit entry records the actual target organization. A lead vendor is a leaf: `iam.trg_verify_org_edge()` refuses any organization beneath one (`23514 LEAD_VENDOR_IS_LEAF`), so nothing can sit under a masked vendor.
    - **Nusear-staff-only `app_cmd.iam_*` write commands and data invariants:** Fifteen `SECURITY DEFINER` commands owned by `platform_writer` (bringing `app_cmd.*` to 48 commands), bridged through `src/commands/iam-cmd.mjs` and composed beside `createAppCommands` in `src/commands/app-cmd.mjs` via `createCommandTransport` (`withRequestTx` and `mapPgError` mapping `23P01` to `409`), permit IAM writes in a company database strictly for `nusear_staff` callers holding the command's write right through their Nusear-internal grant (evaluated by `iam.assert_can_write()` and recorded as `'nusear_support'`), refusing every `company_local` caller at the top of every command before any lookup. Runtime commands refuse writing `platform_root` (which `trg_00b_verify_org_version` also forbids archiving), built-in roles (`owner_org_id IS NULL`), Nusear-internal roles, and Nusear's own people, memberships, and grants (those come strictly from the catalog in code and sync). Data invariants enforce: non-delegable owner (`act:coherence.owner.*`) and worker (`act:coherence.worker.*`) powers never addable to any role; `selling_agent`, `retention_agent`, and their copies staying self-only (`requires_self_scope`); empty new roles (`iam_create_role`); role copy preserving catalog constraints (`iam_copy_role`); single-line role revocation (`iam_revoke_role_grant`); immediate person suspension (`iam_set_person_status`) preserving historical `writing_person_id`; creating a person atomically creating their first works-for line (`iam_create_person`); `external_upline` staying open-ended under `platform_root` (`trg_00b_verify_org_edge`); `explicit_people` subjects lying inside the company's own tree (`trg_role_grant_people_verify`) with automatic carry-over (`trg_02_carry_explicit_people`); vendor real-identity guards on create/update/replay; and unconditional View-as refusal (`42501 VIEW_AS_READ_ONLY`). Delegated IAM administration by a company's own users remains deferred to a future release.

## 5. Coherence Engine Interface

1. **Five sequential steps:** Keyed by ISO-8601 statement date (`YYYY-MM-DD`): `coherence.phase1.assign`, `coherence.phase2.attribute`, `coherence.phase3.bible`, `coherence.phase3.adjust`, and `coherence.phase4.emit`.
2. **Workspace layout:** The engine executes inside a clean checkout at the recorded Git commit with `input/` and `runs/` beside it. `assign` replaces `runs/<date>/` and copies `input/` into `runs/<date>/input/`; every subsequent step reads only inside `runs/<date>/`.
3. **Human review pauses:** Human review is mandatory after `bible` and after `adjust`. `adjust` never runs until a Bible review is saved for the current Bible attempt; `emit` never runs until an Adjust review is saved for the current Adjust attempt and an explicit typed confirmation (`"create statements for <date>"`) names the newest Adjust save.
4. **Decisions as records and generated overlay contract (`overlay.csv`):** Decisions are first-class immutable database records in a parent-linked commit chain (`decision_commits` and `decisions`), where every revision explicitly names the immediately preceding decision on the same key (`replaces_decision_id`). The `overlay.csv` file read by the engine is deterministically generated from decision records as of any journal position, fingerprinted in `generated_overlays`, and never treated as the primary source of truth. Generated overlays preserve exact append-only prefix order and match either the 15-column `v2` schema or the legacy 10-column `v1` schema expected by `coherence/overlay.py`.
5. **Single parser rule:** Only Coherence's own Python reader (`coherence.overlay._read`), invoked through the sealed `coherence_overlay_check.py` script in the run's Python environment, may parse legacy approvals files in production code. No fallback JavaScript CSV parser may exist for approvals import in production modules.
6. **Engine-version provenance:** `engine_versions` records `engine_kind` (`legacy_sealed` or an engine copy), optional `upstream_commit`, and optional `patch_diff_sha256` referencing `nusear_code` stored files. Engine copies that emit data-only JSON review configs (`bible.json`, `adjust.json`) and canonical CSV outputs (`canonical_bob.csv`, `coherent_ledger.csv`, `statements_YYYYMMDD.csv`, `emit_metadata.json`) do not require Node, `pnpm`, or legacy HTML wrapper hashes.
7. **Determinism rules:**
   - Clean Git checkout at the recorded commit so Coherence never stamps a dirty `+` suffix onto build IDs.
   - Replay runs restore the original run's `born` timestamp into `run.json` after `assign` so unidentified-policy Bible keys reproduce deterministically.
   - Environment pins UTF-8 locale (`LANG=en_US.UTF-8`, `LC_ALL=en_US.UTF-8`, `PYTHONUTF8=1`) and time zone `America/New_York`.
   - Case-insensitive directory matching (`ALL BOB` vs `All BOB`) is verified before running steps.
   - Relative paths are never trimmed or silently normalized (trailing spaces in folder or file names are preserved verbatim).
8. **Emit modes:** Each run records its Emit configuration (`coherence`, `builtin`, or `generated` with explicit display name, keep-role list, and no-manager entity list), configured from company settings rather than hardcoded company branches.
9. **Book of Business, Coherent Ledger, and Statements per entity:** Each finished Emit materializes Canonical Book of Business (`bob_policies` and 1:1 `bob_policy_financials`), Coherent Ledger (`coherent_ledger_rows`), and chronological statement batches and lines (`statement_batches`, `statement_agency_lines`, and physically separate `statement_upline_lines`) in one `SERIALIZABLE` transaction, enforcing exact `$0.00` tie-out between Book of Business, Coherent Ledger, and entity statements and refusing any second load of the same run.

## 6. Immutable Data Model

All 31 business tables are immutable once written; only operational scratchpads (`review_drafts`, expiring after 30 days and never read by calculations) and the legacy `review_submissions` queue allow controlled operational mutation.

1. **Journal entries (`journal_entries`):** Gapless sequence numbers (`seq`), microsecond-precision UTC (Coordinated Universal Time) timestamps, actor, optional `acting_for`, command kind, unique command key, request fingerprint, JSONB body with per-table commitments across all 30 child business tables, previous entry hash, and SHA-256 entry hash over a canonical text representation.
2. **Company metadata (`company_meta`):** Singleton immutable identity and default Emit configuration for the company database.
3. **Stored files (`stored_files`):** Content-addressed records keyed by `(store_kind, sha256)`, enforcing `object_name = 'objects/' || sha256` with byte size, MD5, and CRC32C checksums.
4. **Engine versions (`engine_versions`):** Label, commits, `engine_kind`, optional `upstream_commit` and `patch_diff_sha256`, toolchain metadata, and fingerprints referencing solely `nusear_code` stored files.
5. **Input versions, entries, and changes (`input_versions`, `input_entries`, `input_changes`):** Standing versions form a strictly linear chain; snapshot versions capture frozen historical inputs. Relative paths preserve trailing spaces verbatim while rejecting case-insensitive twins, Unicode NFC/NFD normalization twins (different byte encodings of the same accented character), and file-versus-folder clashes. Changes record exact `added`, `removed`, `renamed` (byte-identical move preserving file history), and `replaced` diffs. `Sent/` and `Overlay/` entries change only through carry commands or historical import.
6. **Decision commits, decisions, generated overlays, and review queues (`decision_commits`, `decisions`, `generated_overlays`, `review_queue_items`):** Every review save appends an immutable `decision_commits` node linked to its `parent_commit_id` and records each new or changed decision with its key (`record_id`), disposition, edited fields, five `approved_*` facts, actor, `acting_for`, timestamp, run, review save, surface, and database-verified `replaces_decision_id` pointer. `generated_overlays` fingerprints every `overlay.csv` produced for an engine run. `review_queue_items` captures immutable snapshots of `bible.csv` and `adjust.csv` for database-enforced coverage and reconfirmation checks. Legacy `approvals_files` and `approval_rows` remain supported for imported history.
7. **Book of Business, Coherent Ledger, and Statement tables (`run_materializations`, `bob_policies`, `bob_policy_financials`, `coherent_ledger_rows`, `statement_batches`, `statement_agency_lines`, `statement_upline_lines`):** Vertically split Book of Business (zero-dollar `bob_policies` and 1:1 `bob_policy_financials`), 41-column Coherent Ledger rows with row-level split and revenue-bucket constraints, and physically separate agency and upline statement tables. Security-barrier views in `app_views.*` (owned by `NOBYPASSRLS` `platform_view_owner`) compute entity statements per statement date and reconcile to the Coherent Ledger to the exact cent.
8. **Runs, step requests, cancel requests, step attempt events, and artifacts:** Capture run origin (`app`, `trial`, `replay`, `mac_import`, `company_import`), step requests, typed cancel requests, step attempt lifecycle events, and every artifact classified strictly into `data` (`company_data`) or `code_bearing` (`nusear_code`).
9. **Review saves, review drafts, emit confirmations, carries, abandonments, imported standalone files, and verification checks:** Capture synchronous review saves (`saveReviewDecisions`), typed decisions (including `carry_kind = 'decisions'` advancing the standing decision head without mutating carrier `input_versions`), standalone archived files, and persisted audit reports.

## 7. State Machines and Database Invariants

1. **Derived run stages:** Computed on demand by `coherence.run_stage(run_id, as_of_seq)` and never stored mutably: `preparing`, `running a step`, `waiting for Bible`, `waiting for Adjust`, `ready to create statements`, `emitting`, `done`, `failed`, `interrupted`, `cancelled`, and `abandoned`.
2. **Step attempt lifecycle:** `requested` -> `started` -> one of `finished`, `failed`, `interrupted`, `cancelled`, optionally followed by `superseded`. At most one start, one end, and one `superseded` event per `(run, step, attempt_no)`.
3. **Reconciler slot guard:** A dead open attempt may be marked `interrupted` when the company running slot advisory lock (a cooperative database lock bound to one worker connection) is free OR held by a different backend `(pid, backend_start)` than the attempt starter (a replacement worker reconciling before taking new work). PostgreSQL refuses interruption while the original starter still holds the slot.
4. **Immutability and journal chain:** `ENABLE ALWAYS` triggers block `UPDATE`, `DELETE`, and `TRUNCATE` on all 31 business tables even when `session_replication_role = 'replica'`. Journal inserts require `SERIALIZABLE` isolation (the strictest transaction isolation level), exactly one row per `INSERT` statement, gapless sequence numbers, monotonic timestamps, verified hashes, and `created_xid = pg_current_xact_id()` so no child row can attach after a transaction commits.
5. **Per-entry commitments:** Every journal entry declares exact row counts and canonical SHA-256 content hashes for all 30 child business tables, verified by a deferred `COMMIT` constraint trigger directly inside PostgreSQL (with optional stored canonical list objects on `input_versions`).
6. **Decision replacement chain and review guards:** A deferred trigger verifies every `decision_commits` batch's count, contiguous row order, canonical hash, and exact `replaces_decision_id` pointer via SQL `LAG` along the parent commit chain. Synchronous review saves (`saveReviewDecisions`) run in one `SERIALIZABLE` transaction, enforce 100% `review_queue_items` coverage and Adjust `needs_reconfirm` freshness, refuse stale journal positions, refuse duplicate saves, and refuse writes while viewing as another user. A Bible review may be re-saved while waiting for Adjust only before any Adjust review is saved for Adjust's current attempt, superseding the prior Adjust attempt and requesting a new Adjust step atomically. Drafts are bound to the current finished attempt and forbidden after Emit finishes.
7. **Accounting conservation and entity isolation:** A deferred trigger on `run_materializations` rejects any Emit whose Book of Business totals differ from policy-linked Coherent Ledger splits or whose cumulative entity statements disagree with Coherent Ledger totals by even `$0.01` on any entity, upline total, or record balance. Least-privilege `NOINHERIT`, `NOBYPASSRLS` `platform_*` roles combined with physical table separation, `FORCE ROW LEVEL SECURITY`, and `security_barrier` views in `app_views.*` restrict every caller strictly to its IAM-authorized scope and permitted columns (returning zero rows when `app.session_token` is unset).
8. **Carry and abandon guards:** Only `app` and `company_import` runs in stage `done` may be carried (`trial`, `replay`, and legacy host imports are never carried). At most one sent statement per date is allowed. Carried decisions must extend the current standing decision head (or record `nothing_new = true` when unchanged). Abandoning requires no open attempt (when stage is `emitting`, allowed only while queued before `emit` starts), no pending review submission, and zero carries.

## 8. Failures, Races, and Reliability

1. **Running slot and liveness:** One worker holds the company running slot on a dedicated PostgreSQL connection. Liveness queries run strictly between transactions with a bounded timeout. On connection or slot loss, all in-flight work aborts and no attempt end event is written; the reconciler marks the attempt `interrupted` before any new work begins.
2. **Process-group control and cancel resilience:** Each Coherence step runs in its own detached process group so cancel, timeout (default 15 minutes), or slot loss stops all child processes (including build tools). Cancel-poll errors are logged cleanly and escalate to stopping the step after a bounded consecutive-failure threshold. Non-`ESRCH` kill errors (such as `EPERM`) are logged and surfaced, never silently ignored.
3. **Optimistic concurrency and idempotency:** Every mutating command carries a unique `commandKey` (resending an identical request returns the first result; reusing a key with any changed field is refused with `409`) and an `expectedJournalSeq` checked inside the `SERIALIZABLE` transaction so stale screens are rejected.
4. **Non-blocking review submissions:** The web endpoint stages bytes outside `objects/<sha256>` and queues a pending submission; the worker validates with Coherence's sealed checker, promotes bytes only after checks pass, and records the save atomically in one transaction so bad files never stall the queue.
5. **Create-only verified promotion:** Object uploads require `checksPassed: true`, enforce create-only semantics (`ifGenerationMatch=0` on Google Cloud Storage, atomic hard-link on local filesystem), and verify both MD5 and CRC32C on write and on reuse.
6. **Isolated workspaces and frozen-input verification:** Every step builds a fresh temporary directory verified by SHA-256, excludes code-bearing artifacts (`bible.html`, `adjust.html`) from computation workspaces, re-hashes `runs/<date>/input/` after every step, and removes the temporary directory in a `finally` block.
7. **Batched writes and lossless rebuild:** Multi-row writes use batched `unnest` queries. Exporting the journal as NDJSON and replaying it into an empty migrated database reproduces every record, ID, hash, and commitment identically.

## 9. History Import and Takeover Verification

1. **Manifest-first read-only import:** A company-agnostic JSON manifest declares every read-only source root with no company names in code and verifies that every explicitly configured folder and file exists before importing: legacy host and company run folders, abandoned company runs, standing `input/`, company environment files (`audit.json`, `replaced/`, `finished/`, `answer-key-*.json`, `staging/`, `documents/`, `inventories/`), a local mirror folder of cloud lists and objects (the importer never uses the network), the Incident Report folder, pre-Coherence sent statement files and method-change corrections, and all eight legacy SQLite tables. Legacy SQLite files are never queried live: the importer takes one consistent snapshot copy (`VACUUM INTO`) into its temporary folder, refuses direct opens whenever `-wal` or `-shm` sidecars exist unless that consistent copy is taken, and reads table counts, all eight tables, and sent provenance from that one copy inside one read transaction. Missing Git commits fail the import report unless explicitly allow-listed; unreadable or corrupt SQLite inputs fail immediately. Code-bearing files (verified by full-buffer content scanning as well as path rules) go exclusively to `nusear_code`. All path- or label-bearing command keys are hashed so long paths never exceed the 200-character `command_key` limit. Re-importing the same manifest adds zero records and zero stored files (idempotency), including when standing `input/` already holds a company-sent `Sent/statements_<date>.csv` (every manifest-declared sent date with a finished Emit is excluded from standing base entries whether or not its carry already exists).
2. **Historical overlays into decision records and Layer 2 reconstruction:** Every historical overlay checkpoint listed in a manifest (frozen prior `input/Overlay/overlay.csv`, each Bible save, each Adjust save, `emits/overlay.csv`, company-run review saves, standalone manifest checkpoints, and standing `Overlay/overlay.csv`) is imported in chronological order (same-date runs ordered by recorded start with drafts, archives, and abandoned runs before the primary run, and manifest standalone checkpoints merged by timestamp rather than appended, normalizing manifest checkpoint `originalAt` through the same local-time parser as `run.json` times and storing standalone file `originalAt` values as normalized UTC so commitment hashes and PostgreSQL agree under any server time zone), parsed strictly through `python/coherence_overlay_check.py --parse-only` (no JavaScript CSV fallback) into prefix-chained `decision_commits` and `decisions` with database-verified `replaces_decision_id` pointers. Divergent branches attach to their deepest matching ancestor commit; any prefix mismatch fails loudly naming the run, the checkpoint, and the first differing row number (never a silent reset). Imported overlay rows with a blank `committed_at` generate blank (no `decided_at` fallback for imported rows). Layer 2 verification regenerates `overlay.csv` at each imported commit, parses both original and generated CSVs through the same Python reader, confirms identical header contract (`v1` or `v2`), row count, order, and all 15 normalized cells, verifies 100% valid replacement chains, confirms parity of `decisions_current()` and `decisions_bible_applied()` with the reader's current and Bible answers, fails if zero checkpoints were checked on a populated import, and records the PHI-free result in `checks` (`overlay_reconstruction`).
3. **Preserving company-environment run state, abandonments, and provenance:** Real runs made in a company environment are imported as distinct `company_import` runs exactly as recorded there, including whether the environment recorded a run as sent (with provenance citing the environment record it came from), never dropped and never upgraded; any declared sent record whose run lacks its finished Emit statements file is listed in `problems`. Imported abandoned company runs are recorded in `coherence.abandonments` atomically during `import_historical_run` (so PostgreSQL enforces that they are never published, never carried, and never visible through scoped entity views, while post-import abandonment of normal imported runs remains forbidden), and every file of a partly finished or zero-step abandoned run is retained so Layer 1 rebuilds it byte for byte.
4. **Pre-Coherence sent dates and method corrections:** Historical pre-Coherence sent statement dates and deterministic method-change corrections are parsed through a small Python bridge calling Coherence's own legacy reader and stored as `statement_batches` (`historical_sent`, `method_correction`) with physically separated `statement_agency_lines` and `statement_upline_lines`. On the split layout, `ULTotal` is read before skipping rows with blank `DLTotal`, and no `$0.00` agency line is emitted when only the upline has money. Split reallocations round exactly as Coherence's `_split_money` does (`downline = (amount * Decimal(str(split))).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`, `upline = amount - downline`) and fail loudly if `unreversedOnly` is set without a readable `sentDir` or if `agents.lookup()` returns no split under `useAgentsSplit`. Every `method_correction` specification must declare integer `expectedAgencyNetCents` and `expectedUplineNetCents`; any difference of even one cent aborts the import, naming only the correction and the two totals.
5. **Storage proof (Layer 1, no lost history):** Every imported historical run (including partly finished and zero-step abandoned runs) retains all of its files (including `working/` tables), and Layer 1 verifies byte-for-byte rebuild across every run folder, standing `input/`, the Incident Report folder, and standalone imported areas.
6. **Substance proof (Layer 3 takeover criterion, Gates 1 to 4):** Every statement date gets the full eyes protocol with no sampling: Gate 1 compares every input file by SHA-256 first and stops immediately on any mismatch; Gate 2 compares Canonical Book of Business cell for cell as exact UTF-8 text (parameterized by column list) plus policy status/trajectory metadata; Gate 3 compares the Coherent Ledger cell for cell as exact UTF-8 text plus split and BoB-to-Ledger conservation (`requireConservation: true` requires both ledger split verification and the Book of Business rollup check to have run, and any non-empty unparseable money cell is a violation rather than `$0.00`); Gate 4 compares run delta statements (`statements_YYYYMMDD.csv`) cell for cell and verifies per-entity statement reconciliation and totals, never passing vacuously (when `expectedEntityParity` is given and the left run has no `run_materializations` row, Gate 4 is checked and fails naming that, and `perEntityTotals` is compared over the union of expected and actual entities so unexpected extra entities fail too). Presentation files (`viewer.html`, `bible.html`, `adjust.html`) and per-recipient bundles or agent-level calculations are excluded from substance takeover comparisons. All exported comparator functions (`compareCsvExactText`, `compareRunFolders`, `compareDbRuns`) and check reports are strictly PHI-free: counts, SHA-256 digests, column names, row numbers, and cent deltas only, never raw cell arrays, member names, Medicare numbers, addresses, phone numbers, or `record_id` values.
7. **Point-in-time rebuild (Layer 4) and non-vacuous negative proofs (Layer 6):** Exporting the journal as NDJSON and replaying it into fresh migrated databases up to midpoint and tip cutoffs (inserting `approvals_files` topologically by `extends_sha256` and `decisions` parent commit first, then `row_order`, then `replaces_decision_id`) must match the source database across all 31 business tables (excluding only session-ephemeral `created_xid`, `slot_backend_pid`, and `slot_backend_start`), derived run stages, standing inputs, and generated overlays. The read-only proof runner (`scripts/prove-history.mjs`) runs strictly in pinned local mode against local PostgreSQL hosts (`PGHOST` Unix socket or loopback, strictly refusing any socket path under `/cloudsql`) and `test_*` databases, fails missing comparator runs or folders by name, and cleans its temporary folder on completion or error. Layer 6 runs five mandatory negative mutations on throwaway `test_*` databases (Bible decision mutation, Adjust decision mutation, comparator sensitivity on `$0.01`, `'100.00'` vs `'100'`, and entity swaps, Gate 1 input mutation, and NDJSON tamper/cutoff isolation) confirming each fails at the exact expected gate.
8. **Generic entity-mapped comparison:** When comparing runs across different entity-display configurations, entity mapping is driven by company configuration (`targetEntity`, `preserveEntities`), and bundle manifest verification checks every required file declared by each bundle.
9. **Working-table retention policy:** Imported historical runs retain `working/` table bytes in `company_data` so folders always rebuild byte for byte. New runs whose replay determinism is proved may omit derivable `working/` bytes from object storage; when needed, the worker rebuilds `working/` on demand and verifies every rebuilt file's SHA-256, byte size, MD5, and CRC32C against recorded `coherence.artifacts` before proceeding.

## 10. Security, Member Data Confidentiality, and Retention

1. **No member data in logs, errors, or URLs:** Record IDs (both Coherence's pipe-delimited `carrier|channel|subject|amount|stamp` format and tilde-delimited format) embed member names, policy numbers, and Medicare Beneficiary Identifiers (MBIs). All logs, HTTP errors, database error mappings, comparator reports, proof runner summaries, and Python checker error streams must scrub or withhold member data. Record IDs are forbidden in URL paths and query strings (`POST /approvals/history` and `POST /decisions/history` take a JSON body; `GET` returns `405`).
2. **Code isolation:** Engine files and code-bearing HTML/JS artifacts never enter `company_data` (verified across full file buffers, not just file head/tail) and are never served to customer roles. Review configs are extracted as JSON on the server; `viewer.html` and review HTML never leave Nusear's server.
3. **Database connection and privilege hardening:** Cloud SQL connections use one PostgreSQL 17 server per environment (separate development and production servers holding one database per company plus `nusear_control`) with a public IPv4 address (`ipv4Enabled: true`) and zero authorized networks (`authorizedNetworks: []`) so direct TCP connections are blocked and every connection passes exclusively through the Cloud SQL Connector / Auth Proxy with no relay machine, TLS (`requireSsl: true`, `sslMode: ENCRYPTED_ONLY`), IAM (Identity and Access Management) database authentication (`cloudsql.iam_authentication = on`) with zero static passwords, and `pgaudit` with `log_parameter = off` and `log_parameter_max_length = 0`. Runtime roles follow the `platform_*` least-privilege model: each dedicated IAM login user maps to at most one runtime platform role (`platform_app`, `platform_worker`, `platform_readonly`, `platform_auth_lookup`, or `platform_iam_sync`) via non-inherited `SET`-only membership (`WITH ADMIN FALSE, INHERIT FALSE, SET TRUE`) with zero direct privileges of its own and enters its target role at connection startup via PostgreSQL startup option `-c role=<platform_role>` (zero application-side `SET LOCAL ROLE`, fail-closed when omitted or reset). `platform_app` holds zero base-table privileges (reading only `app_views.*` and executing allowlisted `app_cmd.*`), `platform_worker` holds `SELECT` only on Coherence domain tables and writes strictly through `app_cmd.*`, `platform_writer` holds only `SELECT` and `INSERT` on the 31 business tables (preventing table lock escalation), `platform_readonly` holds `SELECT` only, `PUBLIC` and retired pre-IAM roles hold zero privileges, and every function across all managed schemas pins `SET search_path = pg_catalog`. Local development `pg_hba.conf` forbids `trust`, `md5`, and cleartext `password` rules.
4. **Review-app drift detection:** Copied review-app components are verified against Coherence's committed `web/src/adjust` source tree and approved copy hashes; unreadable repositories or missing tags fail closed unless offline copy-only checking is explicitly requested.
5. **Records retention:** Nothing is retention-locked during development. Production retention periods will be configured after development completes to satisfy HIPAA (Health Insurance Portability and Accountability Act, 6 years under 45 CFR 164.316(b)(2)(i)) and CMS (Centers for Medicare and Medicaid Services, 6 years for marketing/sales recordings under 42 CFR 422.2274(g)(2)(ii) and 10 years for Medicare Advantage books, records, and contractor audit rights under 42 CFR 422.504(d) and (i)(2)).

Cloud SQL development exception (owner ruling, 2026-11-27): Cloud SQL itself (grantor cloudsqladmin) grants cloudsqlsuperuser membership in platform_iam_sync, platform_readonly, platform_versioner, platform_view_owner and platform_writer, which no database user can revoke; verifyIamConfigInvariants accepts exactly those rows (no admin option) only when iam.database_context.environment is dev, and refuses them in production.

## 11. Downstream Readers and Screens

1. **Downstream readers:** Book of Business, Coherent Ledger, Performance, Policy Reconcile, Canon, and signed agent feeds read from the company's newest finished, non-abandoned `app` or `company_import` run (excluding `trial`, `replay`, and legacy host imports) strictly through `app_views.*`. Entity-manager bundle resolution uses explicit configuration and fails with `AMBIGUOUS_ENTITY_BUNDLE` if multiple bundles match a fallback lookup. Signed agent feeds enforce HMAC-SHA256 replay protection and rely strictly on PostgreSQL RLS and `app_views.v_current_policy_periods` for row scoping and zero-dollar `NULL` projection.
2. **Web screens:** Server-side endpoints cover Inputs (version history, diffs, staging, include with reason), Runs (launch, step status/logs, review JSON config, drafts, non-blocking review submit, typed Emit confirmation, data-only outputs, carry sent/approvals, cancel, retry, abandon, review-app drift check), History ("as of" queries, run journal, POST-only approval key history), Checks (list, inspect, and trigger chain/commitments/objects verification requiring a distinct read-only pool or failing cleanly with `503 CHECK_READER_NOT_CONFIGURED` and `mapPgError` mapping), and read-only R1 view screens: Canonical Book of Business (`/views/bob`, `/views/bob/policies/:policyId`, with run picker, KPI totals, non-PHI filtering/sorting/pagination, drawer joins, and authorized-only CSV export), Coherent Ledger (`/views/ledger`, `/views/ledger/transactions/:txId`, with `$0.00` variance check, run/`asOfSeq` selection, drawer joins, and CSV export), Statements per Entity (`/views/statements/batches` carrying `is_sent` from Migration 011 and `marked_sent` upline status, `/views/statements/matrix` single-date or cumulative with pivoted CSV export, `/views/statements/lines` with provenance and CSV export, and `/views/statements/reconciliation` live conservation tie-out), and View-as candidate listing (`/iam/view-as-candidates` over `app_views.iam_people`, `app_views.iam_organizations`, `app_views.iam_memberships`, `app_views.iam_agent_affiliations`, `app_views.iam_role_grants`, `app_views.iam_roles`, and `app_views.iam_my_context`). All R1 view endpoints are strictly `GET`-only (`405 METHOD_NOT_ALLOWED` on non-GET), execute strictly through `app_views.*` inside `inReadTx`, enforce E1 to E5 member, money, unsent-run, vendor-masking, and View-as boundaries inside PostgreSQL, and expose zero existence oracles on refusals. Per-recipient bundle endpoints are absent and refused (`404`). Responses set `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, and a non-sandboxed Content Security Policy (CSP) header.
